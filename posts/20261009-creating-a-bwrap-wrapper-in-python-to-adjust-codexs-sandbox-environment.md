When using Codex in a Linux environment, you may want to adjust the Bubblewrap (`bwrap`) sandbox configuration.

However, directly modifying the `bwrap` arguments generated by the Codex core has a high dependency on the implementation and version.

Therefore, I created `bwrapwrap`, a Python wrapper that mediates the launch of `bwrap`.

This wrapper rewrites some of the mount settings specified by Codex and adjusts how the home directory is handled. It also logs the arguments and environment variables that are actually passed, making it easier to check the sandbox's behavior.

## What I want to achieve with bwrapwrap

This wrapper mainly has the following four roles:

1.  Convert `--dev /dev` to `--dev-bind /dev /dev`.
2.  Detect a bind mount for the working directory and add a mount setting for the home directory immediately before it.
3.  Make the Codex executable and related directories accessible from within the sandbox.
4.  Save the `bwrap` launch arguments and environment variables to a log.

The important thing is that instead of replacing all the arguments generated by Codex, only the necessary parts are modified.

The other arguments are basically passed on to the actual `bwrap` as is.

## 1. The entire code for the wrapper

Python 3 was used for the implementation.

```python
#!/usr/bin/env python3

import os
import sys
import shlex
import pwd
import subprocess
from pathlib import Path
from datetime import datetime


def is_under_home(path: str, home: str) -> bool:
    return path == home or path.startswith(home + "/")


def format_args(args: list[str]) -> str:
    return " ".join(shlex.quote(arg) for arg in args)


def main() -> None:
    os.umask(0o077)

    home = os.environ["HOME"]
    pwd_path = os.environ["PWD"]

    real_bwrap = os.environ.get("BWRAP_REAL", "/usr/bin/bwrap")
    log_file = os.environ.get(
        "BWRAP_LOG",
        f"{home}/.local/state/bwrap-wrapper.log",
    )

    Path(log_file).parent.mkdir(parents=True, exist_ok=True)

    timestamp = datetime.now().astimezone().isoformat(timespec="seconds")
    user_name = pwd.getpwuid(os.getuid()).pw_name
    pid = os.getpid()

    original_args = sys.argv[1:]
    args = []

    tmpfs_inserted = False

    i = 0

    while i < len(original_args):
        arg = original_args[i]

        # Convert --dev /dev
        if (
            arg == "--dev"
            and i + 1 < len(original_args)
            and original_args[i + 1] == "/dev"
        ):
            args.extend(["--dev-bind", "/dev", "/dev"])
            i += 2
            continue

        # Convert --bind
        if arg == "--bind" and i + 2 < len(original_args):
            src = original_args[i + 1]
            dst = original_args[i + 2]

            # If both SRC and DST are exactly the same as PWD
            if src == pwd_path and dst == pwd_path:

                # Insert tmpfs only in the first occurrence
                if not tmpfs_inserted:
                    args.extend([
                        "--tmpfs", home,
                        "--dir", f"{home}/.codex",
                        "--ro-bind",
                        f"{home}/.codex/packages",
                        f"{home}/.codex/packages",
                    ])
                    tmpfs_inserted = True

            args.extend(["--bind", src, dst])
            i += 3
            continue

        args.append(arg)
        i += 1

    # Log
    with open(log_file, "a", encoding="utf-8") as log:
        log.write("\n========== BWRAP START ==========\n")
        log.write(f"Timestamp: {timestamp}\n")
        log.write(f"User: {user_name}\n")
        log.write(f"PID: {pid}\n")
        log.write(f"Bwrap: {real_bwrap}\n")

        log.write(f"Original args: {format_args(original_args)}\n")
        log.write(f"Modified args: {format_args(args)}\n")

        log.write("\nEnvironment:\n")
        for key, value in sorted(os.environ.items()):
            log.write(f"{key}={value}\n")

        log.write("=========== BWRAP END ===========\n")

    # Equivalent to Bash's exec (replaces the process)
    os.execv(real_bwrap, [real_bwrap, *args])


if __name__ == "__main__":
    main()
```

The following describes each process.

## 2. Changing the way `/dev` is mounted

The first change is replacing `--dev /dev`.

`--dev` in Bubblewrap creates a new device filesystem at the specified location. On the other hand, `--dev-bind` bind mounts the host's device directory.

This wrapper performs the following conversion:

```
# Before the change
--dev /dev

# After the change
--dev-bind /dev /dev
```

The implementation is simple: it iterates through the arguments from the beginning and replaces them only when they match exactly.

```
if (
    arg == "--dev"
    and i + 1 < len(original_args)
    and original_args[i + 1] == "/dev"
):
    args.extend(["--dev-bind", "/dev", "/dev"])
    i += 2
    continue
```

This change allows the sandbox to reference the host's `/dev`.

However, `--dev` and `--dev-bind` are not equivalent in terms of security. It may expand the scope of access to the host's devices, so use it with an understanding of the implications.

## 3. Making the home directory a tmpfs

The core process of this wrapper is adding a `tmpfs` to the home directory.

From the arguments generated by Codex, it looks for a bind mount that matches the following condition:

```
--bind "$PWD" "$PWD"
```

Here, the condition is that both the source and destination must exactly match the environment variable `PWD`.

```
if src == pwd_path and dst == pwd_path:
```

If the condition is met, the following settings are inserted before the bind mount.

```
--tmpfs "$HOME" \
--dir "$HOME/.codex" \
--ro-bind "$HOME/.codex/packages" "$HOME/.codex/packages" \
--dir "$HOME/.local/bin" \
--symlink \
  "$HOME/.codex/packages/standalone/current/bin/codex" \
  "$HOME/.local/bin/codex"
```

### Hiding the Home Directory

```
--tmpfs "$HOME"
```

This specifies that a temporary filesystem is mounted on the home directory within the sandbox.

Instead of showing the entire original home directory, this configuration mounts a temporary filesystem and then adds the necessary directories and files.

For example, suppose the host's home directory has the following files:

```
/home/user/
├── .ssh/
├── .aws/
├── .config/
├── .codex/
├── .local/
└── projects/
```

After overlaying it with `tmpfs`, these will not be visible unless explicitly exposed in the subsequent mount.

However, this alone does not completely block access to the entire home directory. The areas that can be accessed depend on other bind mounts, file descriptors, and subsequent mount settings.

### Exposing Codex Executable

When the home directory is overlaid with `tmpfs`, the Codex-related files placed in it also become inaccessible.

Therefore, the following settings are added:

```
--dir "$HOME/.codex"

--ro-bind \
  "$HOME/.codex/packages" \
  "$HOME/.codex/packages"
```

This creates the `.codex` directory and bind mounts the `packages` under it in read-only mode.

This allows the sandbox to reference the Codex packages while restricting writes to the host's packages.

In addition, a symbolic link to the Codex executable is created:

```
--dir "$HOME/.local/bin"

--symlink \
  "$HOME/.codex/packages/standalone/current/bin/codex" \
  "$HOME/.local/bin/codex"
```

This implementation assumes that Codex is installed in the following location:

```
~/.codex/packages/standalone/current/bin/codex
```

If you are using a different installation method, you will need to adjust this path.

## 4. Restoring the Working Directory with a Bind Mount

Even after the home directory is overlaid with a temporary filesystem, it would be meaningless if Codex could not access the working directory.

Therefore, the original `--bind` is not deleted, but remains in the modified arguments.

```
args.extend(["--bind", src, dst])
```

For example, if the working directory is as follows:

```
/home/user/projects/example
```

The arguments will conceptually be in the following order:

```
--tmpfs /home/user

--dir /home/user/.codex

--ro-bind \
  /home/user/.codex/packages \
  /home/user/.codex/packages

--dir /home/user/.local/bin

--symlink \
  /home/user/.codex/packages/standalone/current/bin/codex \
  /home/user/.local/bin/codex

--bind \
  /home/user/projects/example \
  /home/user/projects/example
```

In other words, the configuration aims to hide the entire home directory first and then re-expose only the working directory.

The intended file structure within the sandbox:

/home/user/

`.codex/`

`packages/` Read-only

`.local/bin/`

`codex` Symbolic link

`projects/`

`example/` Read-write

The actual visibility depends on the combination with the original bwrap settings.

However, this configuration has a prerequisite.

In Bubblewrap, the order of mounts is important, and if the parent path of the target directory does not exist correctly, the subsequent bind mount may fail.

The code does not explicitly create intermediate directories such as `projects`. Therefore, depending on the depth of the working directory and the original `bwrap` arguments, it may be necessary to add `--dir`.

Also, even if the working directory is outside the home directory, the `tmpfs` is inserted if the bind mount of `PWD` matches. If you want to limit this behavior, you can add a check to see if it is within the home directory.

## 5. Inserting tmpfs Only Once

The wrapper also considers the possibility that the arguments generated by Codex may contain multiple bind mounts to the same working directory.

Therefore, the following flag is used:

```
tmpfs_inserted = False
```

When a match is found and the insertion is actually performed, it is changed to `True`.

```
if not tmpfs_inserted:
    args.extend([
        # Mount settings to be added
    ])
    tmpfs_inserted = True
```

This ensures that the `tmpfs` and other added settings are inserted only at the first matching location.

On the other hand, the original `--bind` is always retained.

This is a simple measure to prevent mount settings from being added multiple times.

## 6. Logging the bwrap Execution

Another important feature is the logging function.

Bubblewrap combines multiple mount settings and namespace settings, making it difficult to verify that it is configured as intended.

Therefore, the wrapper records the arguments it receives and the modified arguments.

The default log save location is:

```
~/.local/state/bwrap-wrapper.log
```

The environment variable `BWRAP_LOG` can be set to change it.

```
export BWRAP_LOG="$HOME/bwrap-debug.log"
```

The log records the following:

-   Execution date and time, user name, PID
-   The path to the actual `bwrap` being launched
-   Arguments before and after modification
-   Environment variables at launch

`shlex.quote()` is used to record the arguments.

```
def format_args(args: list[str]) -> str:
    return " ".join(shlex.quote(arg) for arg in args)
```

Even if the path contains spaces or shell special characters, it can be output in a format that makes the argument boundaries easy to understand.

In addition, the file creation permissions are limited by the following setting at the beginning:

```
os.umask(0o077)
```

When a log file is newly created, it usually has permissions that prevent it from being read or written by users other than the owner.

However, the permissions of existing files are not changed.

It should be noted that all environment variables are logged. There is a risk that sensitive information such as API keys and authentication tokens may be included in the logs.

If used regularly, it is safer to exclude highly sensitive environment variables or change the method to record only the necessary items.

## 7. Finally, Launch the Real bwrap with exec

After the argument modification and logging are complete, the actual Bubblewrap is launched.

```
os.execv(real_bwrap, [real_bwrap, *args])
```

Here, `os.execv()` is used instead of `subprocess.run()`.

`execv()` replaces the current process with the specified program instead of creating a new child process.

Therefore, the wrapper does not unnecessarily increase the number of processes in the hierarchy.

Also, if `bwrap` starts successfully, the execution result is returned directly to the caller.

This is a natural implementation for this purpose.

## 8. How to Use

First, save the script in the following location:

```
~/.local/bin/bwrapwrap
```

Grant execution permissions:

```
chmod 700 ~/.local/bin/bwrapwrap
```

Next, check the path to the actual `bwrap`:

```
command -v bwrap
```

In a normal environment, something like `/usr/bin/bwrap` is returned.

If it is installed in a different location, you can specify it with an environment variable:

```
export BWRAP_REAL=/usr/bin/bwrap
```

If the Codex can set or override the path to the external `bwrap`, specify `bwrapwrap` as the execution destination.

Note that simply placing the script does not mean that Codex will automatically use this wrapper.

### Test with a simple argument

First, you can test it with a simple argument:

```
bwrapwrap \
  --ro-bind / / \
  --proc /proc \
  --dev /dev \
  -- \
  /bin/true
```

This example allows you to confirm at least the conversion of `--dev /dev` and the launch process of `bwrap`.

However, because it does not contain a bind mount for the working directory, `tmpfs` for the home directory will not be inserted.

Check the conversion results in the log.

```
tail -n 30 ~/.local/state/bwrap-wrapper.log
```

## 9. Implementation Notes and Areas for Improvement

The `bwrapwrap` created this time is a Python wrapper that partially modifies the Bubblewrap arguments generated by Codex.

It can adjust the sandbox mount configuration without modifying the Codex core and record the arguments actually used.

In particular, the configuration to overlay the home directory with `tmpfs` and re-expose only the files and working directory necessary for Codex execution is useful for adjusting the scope of file access in the sandbox.

However, you need to be aware of security considerations such as the scope of `/dev` disclosure and the original mount settings.

`bwrapwrap` is not an independent security boundary, but should be positioned as a mechanism for adjusting existing Bubblewrap settings.

While Codex's sandbox configuration can be observed and the necessary settings can be gradually adjusted, it is important to remember that the tool does not create a new, completely isolated environment.

| Item           | Notes                                                              |
| ------------- | ------------------------------------------------------------------ |
| `PWD` comparison | Compares strings exactly. Does not consider symbolic links or path variations. |
| `--bind` detection | Only processes `--bind SRC DST` format.                                     |
| Mount order    | Results may vary depending on subsequent mounts and the presence or absence of intermediate directories. |
| Codex path     | Assumes a specific standalone layout.                                            |
| `/dev` disclosure | May expand access to host-side devices.                                        |
| Logs           | There is a risk that sensitive information may leak from arguments and environment variables. |

In addition, the code has a function called `is_under_home()` that is defined but not currently called.

```
def is_under_home(path: str, home: str) -> bool:
    return path == home or path.startswith(home + "/")
```

If you want to insert `tmpfs` only for working directories under the home directory, you can use it as follows:

```
if (
    src == pwd_path
    and dst == pwd_path
    and is_under_home(pwd_path, home)
):
```

However, this check does not resolve symbolic links.

Also, for security purposes, it is important to verify all of the original `bwrap` arguments. This wrapper basically retains the existing settings, so it cannot rule out the possibility that files in the home directory may be exposed through other bind mounts or file descriptors.

## Summary

The `bwrapwrap` created this time is a Python wrapper that partially modifies the Bubblewrap arguments generated by Codex.

It can adjust the sandbox mount configuration without modifying the Codex core and record the arguments actually used.

In particular, the configuration to overlay the home directory with `tmpfs` and re-expose only the files and working directory necessary for Codex execution is useful for adjusting the scope of file access in the sandbox.

However, it is necessary to pay attention to security considerations such as the scope of `/dev` disclosure and the original mount settings.

`bwrapwrap` should be positioned as a mechanism for adjusting existing Bubblewrap settings, rather than an independent security boundary.

It is useful when you want to observe how the Codex sandbox is actually configured with what arguments and gradually adjust the necessary settings.
